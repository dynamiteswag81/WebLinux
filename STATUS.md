- libc: rerun `python build/port-musl.py`, then in `src/musl` run `make lib/libc.a lib/crt1.o` and copy both into the sysroot's `lib/`.
- Gotchas:
  - Backslashes in inline shell heredocs and `python -` scripts get mangled. Write scripts with the editor.
  - Python on Windows writes CRLF unless you use `newline=''`.
  - Host tools need `/usr/bin/gcc -std=gnu17`, not clang.
  - Absolute paths containing spaces break fixdep.
  - Windows command lines max out at about 32K characters; use response files.

## Design (details in code comments)
**Kernel:**
- !MMU, single CPU.
- Every task is a Web Worker running its own kernel instance on one shared memory.
- Context switches pass a baton with atomic notify/wait.
- `current` lives in TLS.

**Interrupts:** a bitmask, `wasm_irq_pending`, set by the host. The kernel services it whenever interrupts get re-enabled, or from the idle loop.

**User programs:** PIE wasm modules loaded by `binfmt_wasm`. They import `linux.syscall`, which is the kernel's export.

**vfork:** a libc macro (setjmp + the `wasm_vfork` syscall). The child borrows the parent's worker. The parent resumes when JS throws the `__c_longjmp` tag.

**fork():**
- Programs linked with `WASM_FORK=1` get Asyncify.
- The JS `linux.fork` import unwinds the stack, saves it along with the shadow stack pointer, then calls `wasm_vfork` with flag 1.
- The kernel snapshots the process's memory (`arch/wasm/kernel/fork.c`).
- The child replays the saved stack and gets 0. When it execs or exits, the kernel restores the parent's memory and JS replays the stack with the child's PID.
- Tested: true fork semantics. The child can return from the function that called fork, and memory is isolated.

**Signals:** the kernel fills a mailbox that libc registered, and the libc syscall wrapper runs the handlers.

**main:** `crt1` handles `main(void)`, `main(argc, argv)` and `main(argc, argv, envp)`, via weak symbols plus GOT/null imports in `kworker`.
